هدف این نسخه: تبدیل تصمیم‌های استقرار به Runbook عملیاتی قابل اجرا توسط یک مهندس — از تهیه سرور تا Go-Live و برگشت‌پذیری؛ هر موردی که هنوز تصمیم مالک را می‌خواهد با ⚠️ و پیش‌فرض پیشنهادی مشخص شده است.

۱. توپولوژی و محیط‌ها
* جریان ترافیک عیناً طبق SAD §۱۲: DNS/CDN → Reverse Proxy → (محتوای استاتیک چهار محصول + Backend API) → PostgreSQL؛ و از خروجی: Backup Storage جدا از سرور اصلی.
* نسخه اول تک‌سرور (VPS) است؛ مرزهای ماژول SAD اجازه می‌دهد در نسخه‌های بعد API و Worker و DB بدون تغییر کد جدا شوند — این تصمیم هزینه نسخه اول را کم نگه می‌دارد.
Table: محیط | دامنه | داده | کاربرد
Development	localhost، دامنه‌های *.test	Seed ساختگی	توسعه و آزمون واحد
Staging	staging.khabavar.ir و زیردامنه‌ها	کپی ماسک‌شده	پذیرش، UAT، دروازه‌های کیفیت، تمرین بازیابی
Production	khabavar.ir، shop، magazine، admin.khabavar.ir	واقعی	ترافیک واقعی

۲. تهیه سرور و سخت‌سازی پایه (یک‌بار)
* کاربر غیر root برای اتصال، SSH فقط کلید عمومی و بدون رمز، فایروال فقط 80/443 و SSH باز، نصب unattended-upgrades و fail2ban؛ NTP فعال برای صحت مهرهای Audit Log.
* نسخه Ubuntu LTS پشتیبانی‌شده؛ PostgreSQL نسخه واحد با پکیج رسمی؛ Go و Bun فقط برای Build استفاده می‌شوند و روی سرور Production باینری نهایی اجرا می‌شود نه ابزار Build.
* دو حساب سیستمی جدا: khabavar-api و khabavar-worker با homeهای جدا و بدون shell تعاملی؛ هیچ سرویسی با root اجرا نمی‌شود.
* Swap ملایم و limitها برای systemd (MemoryMax و TasksMax) تا خرابی یک سرویس سرور را نکشد.

* هر سه unit از یک باینری واحد (ADR-DB-002) با متغیر نقش KH_ROLE=identity/api/worker اجرا می‌شوند؛ تفکیک unit برای ری‌استارت مستقل و ایزولاسیون منابع است نه تفکیک باینری — رفع مغایرت شماره ۴ سجل تطبیق KH-INDEX-001 (تصمیم مالک 2026-11-25).
* همه unitها با EnvironmentFile=/etc/khabavar/<unit>.env کار می‌کنند؛ فایل‌ها مالک root با دسترسی 600 (مدل مصوب SAD §۱۲ — متغیرها هرگز در مخزن نیستند).
* Health: هر سرویس /healthz (زنده بودن) و /readyz (آمادگی شامل اتصال DB و وابستگی‌ها) دارد؛ systemd WatchdogSec در نسخه دوم فعال می‌شود.
* لاگ ساخت‌یافته JSON به journald با فیلد ثابت trace_id می‌رود؛ چرخش با journald مدیریت می‌شود و خروجی رخدادهای امنیتی به فایل جدا برای بازبینی هفتگی می‌رود.

۴. Reverse Proxy و TLS
* ⚠️ انتخاب Caddy یا Nginx در SAD باز ماند — پیش‌فرض پیشنهادی این نسخه: Nginx با certbot (تدوین‌های بیشتر در منابع فارسی، کنترل کامل rate limit)؛ در صورت تأیید مالک Caddy، بخش rate limit با میان‌افزار API جبران می‌شود.
* چهار Server Block: khabavar.ir، shop.khabavar.ir، magazine.khabavar.ir (استاتیک + پروکسی API) و admin.khabavar.ir (پنل + پروکسی API) — HSTS فعال، HTTP/2، gzip/brotli، سرآیندهای امنیتی KH-DS-001 و CSP سخت‌گیرانه.
* Rate limit لایه پراکسی برای مسیرهای auth/otp (مثلاً ۱۰ درخواست در دقیقه به هر IP) پشت سقف نرم‌افزاری ۵ در ساعتِ CIAM قرار می‌گیرد — دفاع دو لایه.
* کش استاتیک با هش نام فایل و کش بلندمدت؛ صفحه‌های حساس و پنل همیشه no-store.

۵. فرانت‌اند و رازها
* هر محصول پس از Build در /var/www/<product>/release-<tag> می‌رود و symlink فعلی اتمی عوض می‌شود؛ برگشت یعنی بازنشاندن symlink قبلی — چند ثانیه، بدون downtime.
* رازها (DB URL، رمز امضای توکن، کلیدهای درگاه و پیامک) فقط در فایل‌های env سرور؛ فهرست نام متغیرها در مخزن، مقادیر هرگز. چرخش رمز DB و توکن هر ۹۰ روز در تقویم عملیات ثبت می‌شود.
* ⚠️ وابستگی‌های بیرونی باز طبق SAD §۱۴: درگاه پرداخت، سرویس پیامک، Object Storage، CDN (پیشنهاد بررسی ArvanCloud)، Redis — اسلات پیکربندی همه در envها از روز اول خالی گذاشته شده تا جایگزینی آن‌ها فقط پیکربندی باشد نه کد.

۶. روال Release و Rollback
* گام‌ها: تگ → Build باینری + چهار فرانت → اجرای Migration با نقش db_migrator → تعویض symlink فرانت‌ها → جایگزینی باینری و restart واحد → بررسی /readyz و Smoke مستند → اعلام ریلیز در گزارش.
* Migration فقط forward است؛ down در Production فقط اضطراری با یادداشت مکتوب مالک (مطابق Test Strategy §۶).
* Rollback برنامه: برگرداندن باینری قبلی و restart (کد)، بازنشاندن symlink (فرانت)؛ اگر Migration جدید سازگاری نزولی نداشته باشد، نسخه قبلی کد باید تا پایان دوره مشاهده پس از ریلیز حفظ شده باشد — قاعده: Migration فقط با روند سازگار به عقب merge می‌شود.
* هر Release پنجره کم‌ترافیک (۲ تا ۵ بامداد) و خارج روزهای کمپین؛ دو ریلیز هم‌زمان ممنوع — هر ریلیز فقط یک علت تغییر.

۷. پایگاه داده، بکاپ و بازیابی
* اتصال برنامه فقط با نقش app_runtime (حداقل دسترسی)، گزارش‌ها با reporting_reader، Migration با db_migrator و بکاپ با backup_operator — نقش‌ها از Migrations 000010 و هیچ کلاینی با superuser به برنامه وصل نمی‌شود.
Table: پشتیبان | زمان‌بندی | نگهداری | هدف
pg_dump منطقی کامل	روزانه ۰۳:۳۰	۳۰ روز	RPO ≤ ۲۴ ساعت در بدترین حالت
WAL آرشیو پیوسته	هر ۵ دقیقه	۷ روز	RPO ≤ ۱۵ دقیقه — پیشنهاد ⚠️ تأیید مالک
Snapshot کل فایل داده	هفتگی	۴ نسخه	RTO کوتاه‌تر برای فاجعه سرور

* ⚠️ RPO/RTO هدف در SAD باز بود — پیش‌فرض پیشنهادی: RPO ≤ ۱۵ دقیقه و RTO ≤ ۴ ساعت؛ در صورت تأیید، حجم WAL و پهنای باند بازیابی بر همین مبنا تنظیم می‌شود.
* بکاپ‌ها خارج از سرور اصلی (Object Storage یا سرور دوم) و رمزنگاری‌شده؛ هر بکاپ با restore به محیط موقت آزمون می‌شود و «تمرین بازیابی ماهانه» بخشی از UAT و Go-Live است — بکاپ آزمون‌نشده بکاپ نیست.
* دستورهای بازیابی گام‌به‌گام (نمونه‌سازی از WAL تا لحظه توقف، تعویض connstring، بازکردن سرویس‌ها) در پیوست همین سند نگهداری و پس از هر تغییر نسخه PG به‌روز می‌شود.

۹. چک‌لیست راه‌اندازی اولیه (Go-Live Gate)
* همه چک‌لیست Mustهای PRD علامت خورده باشد؛ حداقل ۱۵ Variant از P1 منتشرشده (O-9) و دروازه‌های QC-01 تا QC-05 برای آن‌ها ثبت شده باشد.
* سناریوهای بحرانی KH-TS-001 §۳ در Staging پاس؛ تمرین واقعی بازیابی بکاپ یک‌بار انجام و ثبت شده باشد؛ نقش‌های DB به‌درستی سیم‌کشی شده باشند (بررسی با تلاش عمدی عملیات غیرمجاز).
* درگاه و پیامک واقعی روی Production پیکربندی و یک خرید/استرداد آزمایشی (سفارش واقعی کوچک + لغو + بازپرداخت) کامل شده باشد؛ DNS/CDN و TLS چهار دامنه سبز و Audit Log فعال از اولین تراکنش.
* فهرست تماس اضطراری و دسترسی دوم شخص به سرور ثبت شده باشد — عملیات تک‌نفره بدون بکاپ دسترسی، ریسک پذیرفتنی نیست.
